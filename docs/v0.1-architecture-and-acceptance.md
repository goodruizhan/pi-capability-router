# V0.1 源码分析、改造计划与验收

## 原 fork 的结构

原 `pi-tool-search` 只有 `extensions/index.ts` 一个源码文件。扩展 factory 注册模型工具 `tool_search`。`session_start` 调用 `getAllTools()` 建立工具清单，清空已启用集合并加入默认核心工具；`turn_start` 重新注册带完整工具清单的 `tool_search`，再调用 `setActiveTools()`。`tool_search.execute` 按精确名称验证，加入会话集合，调用 `setActiveTools()`，随后用隐藏 `sendMessage` 提示模型在下一次请求继续原任务。

搜索没有排序：原实现把全部工具名称和摘要写进 `tool_search` 描述，模型自己在目录里选名称。该目录每轮常驻，无法达到架构计划要求的最小启动上下文。`docs/same-turn-race-bug.md` 记录了同一模型回复中加载并调用新工具的限制；V0.1 保留下一请求生效和隐藏续接提示。

## V0.1 改造

| 模块 | 职责 |
| --- | --- |
| `extensions/registry.ts` | 从 Pi 已注册工具建立本地索引，计算 schema 字符估算 |
| `extensions/search.ts` | 本地词法匹配和排序，只返回少量隐藏工具 |
| `extensions/session.ts` | 会话启用集合、幂等加载和统计 |
| `extensions/index.ts` | Pi 生命周期、单一 `capability` 工具、用户命令 |

扩展 factory 只注册工具和命令；`session_start` 初始化本地索引与初始工具集。每次 `turn_start` 重新扫描已注册工具并应用会话启用集合，因此其他扩展稍后注册的工具也可搜索。`capability.load` 仅调用 Pi 官方 `setActiveTools()`，不执行隐藏工具、不绕过原工具权限。加载只增加，不自动卸载。

## 验收方式

1. 使用 `pi -e <本项目>/extensions/index.ts` 启动一次干净会话，确认启动没有扩展错误。
2. 运行 `/capability status`，确认只包含 `capability`、`read`、`bash`、`edit`、`write`（配置可增加核心工具）。
3. 调用 `capability.search` 搜索一个已注册的非核心工具，确认返回名称和简短描述，初始工具列表没有它。
4. 单独调用 `capability.load` 加载该名称，下一次模型请求调用新工具；再次加载应显示 `Already active`。
5. 运行 `/capability stats`，记录本机启动 schema 字符数与全部注册工具 schema 字符数。新会话重复 `/capability status`，确认加载状态清空。
6. 运行 `npm test`。基准要在实际安装了目标扩展的 Pi 环境中测量，不用计划文档里的示例数字替代结果。

当前限制：Pi 可能在同一模型回复中拒绝先 `load` 后立即调用的新工具。扩展在工具描述中要求先单独加载，并在成功加载后发送隐藏续接提示。

## 已执行的检查（2026-09-23）

`npm test` 的 4 个测试通过。真实 Pi 的隔离 RPC 会话使用 `--no-extensions` 加载本扩展成功，初始状态为 `5 / 9 tools`，记录见 `benchmark/pi-rpc-2026-09-23.json`。

随后在正常已安装扩展环境运行 RPC 验证：`session_start` 时注册 38 个工具、schema 估算 65605 字符；Router 启用 5 个工具、3495 字符，估算减少 62110 字符（94.67%），超过 V0.1 的 60% 目标。部分扩展随后继续注册工具；执行统计命令时总数为 96 个、172702 字符，启动快照和当前注册量在命令中分别显示。原始记录见 `benchmark/full-pi-rpc-2026-09-23.json`。以上是 schema JSON 字符估算，不是模型提供商实际计费 token。
